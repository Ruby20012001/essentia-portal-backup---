# Assumptions & Decisions Register

Project-wide register (foundation ruling #7). Every assumption made because
information was missing is recorded here with **why**, **affected modules**,
and **impact if it changes later**. Rulings that resolved earlier open
questions live in [BRIEF_DISCREPANCIES.md](BRIEF_DISCREPANCIES.md).

| ID | Assumption | Why it was made | Affected modules | Impact if changed |
|---|---|---|---|---|
| A-01 | Factory-support departments (PPC, QC, STORE, PACKING) are parented under FACTORY in the org hierarchy. | The brief's production flow (§10) implies it but never states a hierarchy. | Org hierarchy, department analytics roll-ups, reporting. | One `UPDATE public.departments SET parent_id …` — no code changes. |
| A-02 | Factory station codes (CARP, METAL, STONE, UPH, POLISH, FIT, ASSY) are portal-invented. | The brief names stations but assigns no codes anywhere. | Factory Master, PIO assignments, PPC dashboards. | `UPDATE factory.departments SET code …`; nothing references codes by value yet. |
| A-03 | Stations 8–9 exist as `status='reserved'` rows named "Reserved Station 8/9". | Ruling #2: do not invent them; brief says "9" but names 7. | Factory Master, S10 HOD screen. | Activating one is `UPDATE … SET name, code, status='active'` — no schema change (by design). |
| A-04 | PIO chain approvers (Khushpreet → Deepak Ji → Hardesh) are stored as `approver_hint` text with `approver_user_id = NULL`. | Creating accounts with guessed emails for real people would be fabrication; the Keka import will map them. | Workflow engine, PIO module, S4 Hub. | Until mapped, **PIO approval is deliberately blocked** — `actOnWorkflow` refuses an unresolved step and names the intended approver. Mapping is an UPDATE. |
| A-05 | L0/L1 permission rows are generated as allow-everything (except: audit trail immutable for everyone; founder brief read-only for L1). | CLAUDE.md: "L0/L1 see everything"; §26/§36 name L1 approvers. | Every module (via the permission engine). | Row updates in `public.permissions`; engine unchanged. |
| A-06 | L2/L3 matrix rows are conservative defaults derived from explicit brief statements (§5, §16, §26, §30, §36, §39). | The canonical role-permission matrix does not exist (§38 admits it); ruling #3 approved the hierarchy and the engine, not each row. | Every module. | This register + `public.permissions.notes` make each row reviewable; changing one is an UPDATE. Ruby's review of the matrix **is** the §38 test matrix. |
| A-07 | `rbac.audit_mode` defaults to `denials_and_sensitive` (all denials + all approve/reject/delete/export/ai/financial/hr decisions). | Ruling says "all permission decisions logged"; logging every read at 490-staff scale would swamp the audit partitions. Full logging exists behind the config value `all`. | Audit volume, security review. | Change the config row — no deploy. |
| A-08 | Notification delivery is in-app only; whatsapp/email flags stay false. | Twilio and Microsoft Graph are not connected yet. | Notification framework, Communication Spine. | Flip `notifications.enabled_channels` config + implement the channel senders; templates already carry `default_channels`. |
| A-09 | AI defaults: provider `anthropic`, model `claude-sonnet-4-6`; Azure OpenAI and Copilot are registered fail-loud stubs. | Ruling #5 (replaceable provider) + CLAUDE.md stack; the brief's §2 Copilot preference is discrepancy item 10. | AI service, Communication Spine, Knowledge Library, Priority Signals. | Switch = config change + implementing the stub. A misconfigured provider fails loudly, never silently routes to the wrong vendor. |
| A-10 | EH Experience Centre `target_monthly` stays NULL. | Ruling #6: no placeholder financial values; brief gives only Year-1 incentive thresholds. | EH dashboards (S6), EC scorecards. | Plain UPDATE when business sets targets; dashboards must render the "not set" state until then. |
| A-11 | Dev sessions claim only a user ID via `DEV_USER_ID`; access level and department always come from `public.users`. | Keeps RBAC + RLS running against database truth before Entra ID/OTP land; a client cannot claim a level. | Session stub, every permission check. | Deleted wholesale when the auth module replaces `getCurrentUser()`. |
| A-12 | The Rimadesio/Mumbai block is a **config rule** (`eh.rimadesio.blocked_departments`), not a permission row. | It is a product×location restriction (§27), not a level×resource one — it doesn't fit the RBAC shape. Ruling #4 allows documented exceptions. | EH quotation service (S6, not yet built) MUST check this config before generating any quote. | Extending the block list (another EC, another brand rule) is a config edit. |
| A-13 | Keka sync contract: `users.keka_employee_id` links people; `keka.department_mapping` config maps Keka department names → `departments.code`. | Keka is not connected; the Department Master must stay authoritative through the import. | HR module (S11), exit protocol (S12), workflow approver mapping (A-04). | The import job reads the mapping; unknown Keka departments fail the import loudly rather than creating departments outside the master. |
| A-14 | WIO clock escalations (day-12 / lapse) fire via `POST /api/jobs/wio-clock`, deduped per WIO per day — no scheduler yet. | The auto-pilot module (40 events, Brief §36) owns scheduling; building a one-off cron for S4 would be duplicated later. | S4 escalations, future auto-pilot. | Auto-pilot calls the same service on its cadence; the endpoint stays as the manual/ops trigger. |
| A-15 | Dev-only: the PGlite wire server (`npm run dev-db`) is single-connection and can wedge if a client dies uncleanly or a second client connects — restart it. Data is in-memory (restart = fresh fixtures). Auth/timeout logic is therefore verified in the in-process harness, and E2E scripts are HTTP-only. | Zero-install local Postgres; production is real RDS where none of this applies. | Local development + test harness design only. | Disappears entirely once a real Postgres instance is provisioned. |
| A-16 | Entra ID token validation (JWKS signature check, nonce/PKCE, claims→`users.microsoft_oid` mapping) is scaffolded but not implemented — the provider fails loud without a tenant. The redirect plumbing + session minting are complete. | Building/validating OIDC crypto without a real tenant would be untestable and likely wrong; better a fail-loud slot than unverifiable code. | Auth module (Phase 1), all staff sign-in. | When the tenant is provisioned: implement `completeCallback`, set the Entra env, flip `auth.provider` to `entra`. No other module changes. |
| A-17 | Dev users share one scrypt password (`essentia-dev-2026`, single salt) seeded in 900_dev_fixtures. | An in-memory dev seed; real accounts come from Entra and never carry a password. | Local login only. | Deleted with the fixtures once real auth is live. |
| A-18 | Keka has no L0-L3 concept; sync takes access level from the fixture's `accessLevelHint`, and only on INSERT (re-sync never downgrades an in-portal-elevated user). | Access levels are a portal concept, not a Keka field; clobbering them on every sync would undo deliberate elevation. | Keka sync, RBAC. | Live Keka needs a designation→level mapping config (or in-portal assignment); one UPDATE to the sync's INSERT branch. |
| A-19 | Live Keka HTTP provider (`fetchEmployees/Departments`) is a fail-loud slot — request shape scaffolded, field mapping not implemented. | Mapping Keka's payload without API access + a sample response would be guesswork. | Keka sync (live). | Implement the two methods against a real payload; flip `keka.provider` to `http`, set `KEKA_BASE_URL/KEKA_API_KEY`. No other module changes. |
| A-20 | The PIO approval chain is armed by matching seeded `workflow_steps.approver_email` to synced accounts. Changing an approver = update the email seed (or the person's Keka email) and re-sync. | Keeps the chain as data and decoupled from specific user IDs, which don't exist until sync. | Workflow engine, PIO module. | Resolves A-04 (approvals were blocked pending this). Same mechanism extends to future chains (WOs, letters). |
| A-21 | Email channel builds branded HTML but does not send — no SMTP transport is wired; `send()` fails (→ retry/DLQ) without `SMTP_URL`. | No mail server or transport lib in this environment; the HTML (the hard part) is built and unit-tested. | Notification framework (email channel). | Add a transport (e.g. nodemailer) reading `SMTP_URL` + config `email.from_address`; one function body. |
| A-22 | WhatsApp / SMS / Push are prepared interface slots that report 'failed' (→ retry/DLQ), not implemented. | Their gateways (Twilio, FCM/APNs) are not provisioned; the interface + routing + delivery lifecycle are ready. | Notification framework (those channels). | Implement each provider's `send()` against its gateway; register (already done) and add to `notifications.channels_live`. |
| A-23 | Every delivery attempt writes an audit row (`NOTIFICATION_DELIVERY`). At scale this is high-volume. | The Phase-3 spec requires per-notification audit (recipient, channel, event, status). | Audit volume. | If it becomes noisy, gate behind a config flag like the RBAC `audit_mode`; the write is centralised in one place. |
